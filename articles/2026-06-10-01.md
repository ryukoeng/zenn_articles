## ELB とは

**ELB（Elastic Load Balancing）** は、外部からのリクエストを**複数のターゲット（EC2 など）に振り分ける**マネージドなロードバランサーサービス。

- 1 台のサーバーにアクセスが集中しないよう、**負荷を分散**する。
- 異常なターゲットを **ヘルスチェック**で検知し、正常なターゲットだけに振り分ける。
- 複数の AZ にまたがって配置でき、AZ 障害時も**生き残った側で処理を継続**できる。ロードバランサー自体のスケールや冗長化は AWS 側が面倒を見てくれる。

---

## ELB の種類

ELB は総称で、実体は 4 種類ある。現行で選ぶのは実質 **ALB か NLB** の 2 択。

| 種類 | 正式名称 | 動作レイヤー | 主な用途 |
| ---- | ---- | ---- | ---- |
| **ALB** | Application Load Balancer | L7（HTTP/HTTPS） | Web アプリ・API。パスやホスト名で振り分け |
| **NLB** | Network Load Balancer | L4（TCP/UDP/TLS） | 高性能・低遅延が必要な通信、固定 IP が欲しい場合 |
| **GWLB** | Gateway Load Balancer | L3（IP） | ファイアウォールなどセキュリティアプライアンスの挟み込み |
| **CLB** | Classic Load Balancer | L4/L7 | 旧世代。**新規では使わない** |

- 迷ったら、**HTTP ベースの Web アプリなら ALB**、**それ以外のプロトコルや性能重視なら NLB**。

---

## ALB と NLB の比較

| 比較項目 | ALB | NLB |
| ---- | ---- | ---- |
| **振り分けの単位** | URL パス・ホスト名・ヘッダーなど L7 の情報 | IP アドレスとポート（L4） |
| **固定 IP** | × 不可（DNS 名でアクセス） | ○ AZ ごとに固定 IP / Elastic IP を持てる |
| **性能特性** | 機能が豊富な分、NLB よりレイテンシは大きめ | 超高スループット・低遅延 |
| **TLS 終端** | ○ | ○ |
| **WebSocket / HTTP/2** | ○ | ○（TCP として通すだけ） |
| **WAF の適用** | ○ 可能 | × 不可 |
| **リダイレクト・固定レスポンス** | ○ 可能 | × 不可 |

- **「HTTP を理解して賢く振り分ける」のが ALB、「とにかく速く通す」のが NLB** と覚えると区別しやすい。

## 主要な構成要素

ELB は「リスナー」「ターゲットグループ」「ヘルスチェック」の 3 点セットで動く。

| 要素 | 役割 | ひとこと |
| ---- | ---- | ---- |
| **リスナー** | 受け付けるプロトコルとポートを定義（例: HTTPS:443） | リクエストの「受付窓口」 |
| **リスナールール** | 条件に応じて転送先を振り分ける（ALB のみ） | 受付での「案内係」 |
| **ターゲットグループ** | 振り分け先のまとまり（EC2・IP・Lambda） | 転送先の「名簿」 |
| **ヘルスチェック** | ターゲットの生死を定期確認 | 名簿の「点呼」 |

- リクエストの流れは **リスナー → ルール評価 → ターゲットグループ → ターゲット**。
- ターゲットグループの種別は **インスタンス / IP / Lambda** から選ぶ。Auto Scaling と組み合わせる場合はインスタンス指定が基本。

---

## リスナールール（ALB）

ALB はリスナーに**ルール**を複数設定でき、L7 の情報で転送先を変えられる。

| 条件の例 | 内容 |
| ---- | ---- |
| **パスベース** | `/api/*` は API 用ターゲットグループへ |
| **ホストベース** | `admin.example.com` は管理画面用へ |
| **ヘッダー / クエリ文字列** | 特定ヘッダーを持つリクエストだけ別経路へ |

ルールは**優先度の小さい順に評価**され、どれにも一致しなければ**デフォルトルール**が適用される。よく使うのが HTTP → HTTPS のリダイレクト:

| リスナー | アクション |
| ---- | ---- |
| HTTP:80 | HTTPS:443 へリダイレクト（301） |
| HTTPS:443 | ターゲットグループへ転送 |

- HTTPS リスナーには **ACM（AWS Certificate Manager）の証明書**を紐づけて TLS を終端させるのが定番。バックエンドまで暗号化を持ち込まずに済む。

## ヘルスチェック

ターゲットグループごとに設定し、**失敗が続いたターゲットは振り分け対象から外れる**。

| 設定項目 | 内容 | 目安 |
| ---- | ---- | ---- |
| **パス** | チェック先のパス（ALB） | `/health` など軽量なエンドポイント |
| **間隔** | チェックの実行間隔 | 30 秒（デフォルト） |
| **タイムアウト** | 応答待ちの上限 | 5 秒 |
| **正常しきい値** | 連続成功で healthy 扱いになる回数 | 3〜5 回 |
| **非正常しきい値** | 連続失敗で unhealthy 扱いになる回数 | 2〜3 回 |

- ヘルスチェック用エンドポイントは **DB アクセスなどを含まない軽い処理**にしておく。DB 障害のたびに全ターゲットが unhealthy 扱いになる、といった巻き込まれ方を避けられる。
- unhealthy になっても**ターゲット自体が止まるわけではない**。復帰すれば自動で振り分けに戻る。

## 配置とネットワーク設計

ELB は VPC 内のサブネットに配置する。**最低 2 つの AZ** を選ぶのが基本。

| 項目 | 推奨 | 理由 |
| ---- | ---- | ---- |
| **ELB の配置先** | パブリックサブネット（外部公開の場合） | インターネットからの入口になるため |
| **ターゲットの配置先** | プライベートサブネット | 外部から直接到達させないため |
| **AZ 数** | 2 つ以上 | AZ 障害時にも継続稼働させるため |
| **スキーム** | 用途で選ぶ | 外部公開は internet-facing、内部 API は internal |

- 「**入口（ELB）はパブリック、実体（EC2）はプライベート**」が定石の構成。ターゲットのセキュリティグループは、**ELB のセキュリティグループからの通信だけ許可**すると安全。
- **クロスゾーン負荷分散**を有効にすると、AZ をまたいで全ターゲットへ均等に振り分けられる（ALB はデフォルト有効、NLB はデフォルト無効）。

## 料金の考え方

ELB は**起動しているだけで課金される**。検証用に作ったまま放置しないこと。

| 項目 | 課金 |
| ---- | ---- |
| **時間課金** | ○ 起動時間に応じて課金（使わなくてもかかる） |
| **LCU / NLCU** | ○ 処理量（新規接続数・帯域・ルール評価数など）に応じて課金 |
| **データ転送** | ○ 外部向け・AZ 跨ぎの通信量に応じて課金 |

- **LCU（Load Balancer Capacity Unit）** は「どの次元の使用量が一番多いか」で決まる従量単位。小規模なら時間課金が支配的になりがち。
- 検証が終わった ELB は**削除**する。EC2 を停止しても ELB は課金され続ける。

---

## まとめ

- ELB は**リクエストを複数ターゲットに振り分ける**マネージドロードバランサー。現行の選択肢は実質 **ALB（L7）か NLB（L4）**。
- 構成要素は **リスナー（受付）→ ターゲットグループ（名簿）→ ヘルスチェック（点呼）** の 3 点セット。
- ALB は**パス・ホスト名ベースの振り分けや HTTPS リダイレクト**が得意。証明書は ACM で管理して TLS 終端させる。
- 配置は「**ELB はパブリック、ターゲットはプライベート**」が定石。AZ は 2 つ以上に分散する。
- **起動しているだけで課金**されるので、検証後は削除を忘れない。
