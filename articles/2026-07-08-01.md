個人開発や少人数のチームでAWSを触っていると、使う人が増えるたびにIAMユーザーを作って、アクセスキーを発行して、パスワードを共有して……という運用になりがちだ。気づけば「誰にどの権限を渡したか」があやふやになり、アクセスキーの保管場所もばらばら。棚卸しをしようにも、どこから手をつければいいか分からない状態だった。

一番の動機は、そもそも恒久的なアクセスキーを発行して持ち歩く運用そのものをやめたかったこと。そこで重い腰を上げてIAM Identity Centerに移行し、移行後はアクセスキーを一切使わず、ログインのたびに発行される一時的な認証情報だけで運用するようにした。認証はポータルに一元化され、権限管理もアクセスキーの管理も驚くほど楽になった。ここではその過程で整理した内容を備忘録として残す。

---

## IAMユーザー運用の何が辛かったか

| 課題 | 具体的に何が起きるか |
| --- | --- |
| アクセスキー（恒久的な認証情報）の散在 | ローカルの`.aws/credentials`やメモ帳、チャットに埋もれて漏洩リスクが上がる |
| 権限の棚卸しがしにくい | 誰がどのポリシーを持っているか、ユーザーを1人ずつ確認しないと分からない |
| MFAがユーザー任せ | 設定を強制する仕組みがないと、徹底されないユーザーが出てくる |
| 複数AWSアカウントの切替が面倒 | アカウントごとにIAMユーザーを作り、ログインし直す必要がある |
| 退職・離任時の削除漏れ | 各アカウントを回ってユーザーを消して回らないといけない |

いずれも「認証情報と権限がユーザー単位・アカウント単位でバラバラに存在する」ことが根本原因になっている。

---

## IAM Identity Center とは

**AWSアカウントやアプリへのアクセスを一元管理し、シングルサインオン（SSO）でログインできるサービス**。旧称は AWS SSO で、現在の名前に変わっても機能の中心は変わっていない。

IAMユーザーのように恒久的なアクセスキーを個別に配ることはせず、ログインのたびに**一時的な認証情報**が発行される。認証情報が長期間有効なまま放置される、という状態自体が生まれにくい仕組みになっている。

---

## IAMユーザー と IAM Identity Center の違い

| 観点 | IAMユーザー | IAM Identity Center |
| --- | --- | --- |
| 認証情報 | 恒久的なアクセスキー・パスワード | 一時的な認証情報 |
| ログイン方法 | アカウントごとに個別サインイン | アクセスポータルからSSOでログイン |
| 権限の付け方 | ユーザー・グループにポリシーを直接添付 | 権限セットをアカウントに割り当て |
| 多アカウント対応 | アカウントごとにユーザーを作成 | 一箇所（Identity Center）で集中管理 |
| MFA | 任意で個別設定 | 一元的に強制しやすい |
| 棚卸し | 散らばりがちで把握しづらい | 割り当て一覧で見渡しやすい |
| 向いている用途 | プログラムアクセス・レガシーな連携 | 人間のコンソール・CLIアクセス |

これで「IAMユーザーが不要になる」わけではない。アプリやシステムからのプログラムアクセスには、引き続きIAMロールやIAMユーザーが使われる。あくまで**人間がログインする経路**をIdentity Centerに寄せる、という整理になる。

## 仕組みの基礎

内蔵ディレクトリ（Identity Center Directory）を使う前提で、主要な構成要素を整理する。

| 用語 | 役割 |
| --- | --- |
| ユーザー | Identity Centerの内蔵ディレクトリで作成するログインアカウント |
| グループ | ユーザーをまとめる単位。権限セットの割り当てをグループ単位で行える |
| 権限セット（Permission set） | IAMポリシーの束。アカウントに割り当てると実体化する |
| アカウントへの割り当て | どのユーザー/グループに、どのアカウントで、どの権限セットを与えるかの紐付け |
| AWSアクセスポータル | SSOでログインする入口となるURL |
| 一時認証情報 | ポータル経由のログインで発行される、有効期限付きの認証情報 |

権限セットは単なる設定の雛形ではなく、アカウントに割り当てた時点でそのアカウント内に**IAMロールとして展開される**。SSOユーザーはログイン時にこのロールをassumeする、というイメージを持っておくと理解しやすい。

## 移行してよかったこと

- 恒久的なアクセスキーを発行・保存しない運用に統一でき、キーの漏洩リスクそのものがなくなった
- コンソールもCLIも、ログインのたびの一時認証情報だけで完結するようになった
- ログインが一つのアクセスポータルに集約された
- 権限セット単位で管理できるようになり、棚卸しが楽になった
- MFAを入口（ポータル）で一元的に効かせられるようになった
- 多アカウントでも、ポータルからワンクリックでアカウント切替できるようになった

---

## 移行のざっくりした流れ

1. IAM Identity Centerを有効化する
2. 内蔵ディレクトリでユーザー・グループを作成する
3. 権限セットを作成する
4. ユーザー・グループに対して、アカウントと権限セットを割り当てる
5. アクセスポータルからログインして動作確認する

CLIも同じで、`~/.aws/credentials`にアクセスキーを書く代わりに`aws configure sso`でSSOプロファイルを作る。以降はブラウザ認証で得た一時認証情報を使うので、ローカルに恒久的なキーを置かずに済む。

```bash
aws configure sso
# SSO start URL とリージョンを入力し、ブラウザ認証 → 一時認証情報でCLIが使える
```

ハマりどころとしては、恒久的アクセスキー前提で書かれていたツールやスクリプトが、一時認証情報への切替に対応していないことがある点。この場合は、そのツールを一時認証情報（SSOプロファイル）に対応させるか、CI向けにはIAMロール（OIDC連携など）へ寄せて、やはりアクセスキーを持たない形にそろえていく。また、Identity Centerを有効化するリージョンと、実際に作業するリージョンの食い違いにも注意しておきたい。

---

## まとめ

- IAMユーザーは恒久的な認証情報が散らばりがちで、棚卸しやMFA徹底が難しくなる
- IAM Identity Centerは一時認証情報とSSOで、認証を一元的かつセキュアに管理できる
- 移行後は恒久的なアクセスキーを発行・保存せず、コンソールもCLIも一時認証情報だけで運用できる
- 権限セットをアカウントに割り当てるモデルなので、多アカウント運用に強い
- 人間のアクセスはIAM Identity Center、プログラムアクセスはIAMロールという使い分けが基本になる
